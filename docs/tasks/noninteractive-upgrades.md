# 非交互升级与失败分流

本任务由 `pennix-lifecycle` 负责，根仓协调任务为 `11-27-lifecycle-noninteractive-upgrades`。登记维护分支为 `main`，起点为 `49955a2b0baeda83ab7f4bb426ccac14616f24af`。以根仓任务的需求基线、实施合同及现场授权记录为准；本页不替代合同或授权。

- `update --all` 将来源查询失败和实际归属问题都引向 `reconcile`，但该入口不支持 uv/PyPI 安装的 `markitdown`。有 TTY 也会在确认前复现。原 HomeWSL 故障的精确来源错误未知，不把注入用例当作现场根因证明。
- `tool update` 和 `update --all` 独立缺少无 TTY 的受控确认路径。计划复用精确确认与各自原生恢复；不默认信任变化后的候选，不将来源失败、未知归属或需要原生批准的动作转换为成功。
- 已选首版覆盖 Arch 官方与 AUR 包，由管理员独立安装系统所有的固定执行器，运行时仍使用宿主既有授权；允许经审阅且能证明静默窗口的受管 Paseo 重启。验收覆盖查询故障、归属失配、无 TTY 执行、原生包锁内候选漂移、活动工作拒绝、不明事务恢复、旧版回归与真实发行载荷。

## Arch 官方包事务

`native/arch_transaction.c` 是固定执行器的内部事务代码。它在同一个 `libalpm` 持锁事务内核对完整的已装包基线，包括不在候选清单中的包；随后解析完整升级及明确请求的官方包，复核实际包变更，并验证私有暂存中的包摘要与分离签名。未审阅的基线变化、包移除、原生询问和隐式下载均在提交前拒绝。进入原生提交后若报错，按结果未知处理，不以退出码断言未写入。

提交前在执行器自有目录中持久化步骤 ID 和请求摘要，阻止同一步骤重放；只有 `libalpm` 报告事务完成且提交过程中没有错误时才补记完成。回执缺失、不完整或摘要不匹配均不能证明完成，即使包版本已经相同。

`pennix recover --resolve completed` 对已开始或结果未知的非交互 Arch 系统包步骤，只使用系统所有的固定观察入口核对同一事务、用户和冻结请求的原生回执。它还核对包数据库未被锁定、完整已装包集合符合预期，以及 `pacman -Dk` 通过，才记录原生包步骤完成。组件归属另有记录步骤：包已提交但归属回执或组件锁写入中断时，恢复只在重新核验原生完成回执、实际包和冻结锁后补齐记录，不重新提交包。原生包步骤通过不代表整个升级已完成。

在备有 C 编译器、`libalpm` 开发头、`repo-add` 和 GnuPG 的 Arch 环境，可运行隔离回归：

```bash
PENNIX_TEST_ARCH_TRANSACTION=1 python3 -m unittest discover -s tests -p test_arch_transaction.py -v
```

测试驱动只接受夹具路径，不得安装为系统执行器。`bash native/build.sh /绝对路径/新暂存目录` 由普通用户构建独立系统载荷，不安装文件或修改 `sudo` 配置。载荷分别提供 `arch-commit` 提交入口和 `arch-executor observe` 观察入口，依赖宿主的 Python 和 `libalpm.so.16`。提交入口只收绑定事务、调用者和摘要的结构化请求，不收命令、自定义数据库或缓存路径。

固定提交入口从系统所有的 pacman 配置及其 `Include` 文件读取策略。当前仅支持可核验的绝对 `Include` 路径，不支持通配符。入口要求所需仓库数据库、包工件和分离签名已在受信的本机位置，复制工件到私有目录后不联网下载；在持包锁的提交点重新检查配置和 Hook。`pennix update --all --confirm` 已接入此入口，覆盖官方包完整升级及明确选中的缺失官方组件。写入前重新核对执行器身份和精确候选；原生请求结果未知时不回退到旧的 `pacman` 路径，也不重放请求。固定入口已在断网 Arch 容器验证，正式部署来源、原生授权和回退仍须单独验收。

无 TTY 全量入口在隔离同步库中使用 `pacman -Sup` 重新求解，收集候选文件名、SHA-256 和整组依赖。预演绑定 `pacman-conf` 展开的配置及有效 Hook 文件；后置目录的同名 Hook 优先，`/dev/null` 屏蔽明确记录。`pacman --print` 可能静默接受替换，所以含声明替换的候选不会进入这条路径。只读清单是执行器的比较输入，不替代执行器在真实包锁内核验。

## AUR 工件的事务核验

同一原生事务可接收由管理员单独审批的 AUR 包。构建审阅摘要只授权构建，不能用来确认安装：

1. 对 `workflow.config` 已选、来源已登记的组件运行 `pennix aur-prepare <组件 ID> --plan --json`。核对 Git 提交、配方、对应架构的来源及其 SHA-256。预览不执行配方、不安装依赖。
2. 用 `pennix aur-prepare <组件 ID> --confirm <构建审阅摘要> --json` 构建。Lifecycle 核对原材料后，由普通用户在断网的 `bubblewrap` 中运行 `makepkg`，输出工件路径、版本、Git 提交和 SHA-256，不安装工件。
3. 管理员独立核对并签署工件。固定入口仅从系统所有的 `/var/lib/pennix-aur/<原生包名>/` 读取 `approved.json`、包本体和同名 `.sig`。审批记录字段为 `version`、`ref`、`filename`、`sha256`、`signature_sha256`、`signer`；`signer` 是该签名在系统 pacman keyring 中可信的完整 40 位大写指纹，不能用升级请求选定不同指纹。该目录及文件须由 root 所有，不接受符号链接、组或其他用户写权限。同一次事务中的 AUR 包须使用同一已批准签名身份。初始化系统信任和部署固定入口均须另外由管理员完成，构建命令不改变这些设置。
4. 再运行 `pennix update --all --plan --json`。对照工件、分离签名摘要和实际写入步骤；如预览报告缺依赖，先独立审阅并准备所需依赖，再重新生成摘要。只将新的安装审阅摘要交给 `pennix update --all --confirm <升级审阅摘要>`。固定入口会在 `libalpm` 包锁内核对包身份、可信签名及完整实际包集；不允许替换现有包、降级或增加未审阅的依赖。

构建入口目前只接受 `.SRCINFO` 列出的冻结本地文件或 HTTPS 来源，并要求对应具体 SHA-256；不执行缺摘要的来源，也不使用 `makepkg --syncdeps`。只读安装预览不能替代固定入口的真实签名核验。没有已审阅的可信系统工件时，不能绕回旧安装路径。

在上述 Arch 测试命令中同时设置 `PENNIX_TEST_ARCH_BUILD=1`，可重复验证隔离构建和本地签名包。另用 `agent-of-empires-bin` 的冻结真实配方，在普通用户沙箱构建后，由一次性 Arch 容器的测试签名者和正式依赖验证固定路径：普通用户预览不安装，签名或审批记录变化时拒绝，匹配时提交，可观察完成且不能重放。测试信任不用于正式宿主。

## Paseo 停止态下更新 CLI

关闭自启动不能证明 daemon 已停止。只读 `pennix update --all --plan` 可以在 daemon 运行时展示已核验的候选、写入步骤和审阅摘要。若包含 Paseo CLI 更新，结果列出 `paseo-daemon-stopped` 执行前置条件；`execution_ready: false` 表示当前还不能执行，不表示预览失败。该路径不安排启动或重启。

`--confirm` 核对摘要后，只有本机原生回执证明同一目标 daemon 已停止、且未请求启动时，才允许进入写入流程。只停止 daemon 不改变已审阅的操作，因此在目标、配置、候选和其他写入条件均未变化时，原摘要仍可用。CLI 写入前和写入后再次核对；写入后失去停止态证据时保留事务。不能从依赖该 daemon 的会话停掉 daemon 来完成确认。
